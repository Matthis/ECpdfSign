# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

ecpdfsign is a Tauri v2 desktop app with a vanilla TypeScript frontend (no framework) built by Vite. It renders PDFs with pdf.js and will write them with pdf-lib. Unit tests run with Vitest (`src/**/*.test.ts`) and `cargo test`; there is no linter or formatter configured yet.

## Commands

- `npm run tauri dev` — run the desktop app (starts Vite on port 1420 via `beforeDevCommand`, then compiles and launches the Rust app)
- `npm run tauri build` — production bundle (runs `npm run build` first; frontend output goes to `dist/`, bundles to `src-tauri/target/release/bundle/`)
- `npm run build` — frontend only: `tsc` type-check (`noEmit`) followed by `vite build`
- `npm run dev` — Vite dev server only (the frontend runs in a browser, but `invoke` calls fail outside the Tauri webview)
- `npm test` — Vitest unit tests (Node environment)
- Rust side, from `src-tauri/`: `cargo check`, `cargo test`, `cargo clippy`

On this machine `npm` may not be on PATH in Claude's shell. Node.js lives at `C:\Program Files\nodejs`, so prepend it (`$env:Path = "C:\Program Files\nodejs;$env:Path"`) or call `npm.cmd` by full path.

## Architecture

There are two halves that talk over Tauri IPC:

- **Frontend** (`index.html`, `src/`): plain DOM code. `src/app.ts` holds the DOM-free open/select flow (`createApp(deps)`, unit-tested with fakes); `src/main.ts` only wires it to the backend and the DOM views in `src/ui/` (pure layout math in `src/ui/layout.ts`); `src/model.ts` holds document state; `src/pdf/` is the only code that touches pdf.js (import it via `src/pdf/pdfjs.ts`, which picks the legacy build). Screen <-> PDF coordinates go only through `src/pdf/viewport.ts`. Rust is called via the typed wrappers in `src/backend.ts` (`invoke` from `@tauri-apps/api/core`; argument keys are camelCase on the JS side and map to snake_case Rust parameter names).
- **Backend** (`src-tauri/`): `src/main.rs` only calls `ecpdfsign_lib::run()`. All real code lives in `src/lib.rs`, where the `tauri::Builder` registers plugins and commands. The backend owns file access: it shows the dialogs, keeps the source path in managed state and returns bytes; the frontend never sends paths. The lib/bin split, with the `_lib` crate name, is needed for Windows and mobile builds, so keep it.

To add a backend command:
1. Write a `#[tauri::command]` fn in `src-tauri/src/lib.rs` (or in a module it pulls in).
2. Add it to `tauri::generate_handler![...]`.
3. Add its name to the `AppManifest` command list in `src-tauri/build.rs` and grant `allow-<command-name>` (dashes) in `src-tauri/capabilities/default.json`; otherwise the call is rejected at runtime.
4. Call it from TS with `invoke`.

To add a Tauri plugin:
1. Add the npm package and the Cargo crate.
2. Call `.plugin(...)` in `lib.rs`.
3. Grant its permissions in `src-tauri/capabilities/default.json`. The capability applies to the window labelled `main`, and missing permissions cause runtime IPC errors, not compile errors.

Config notes:
- `src-tauri/tauri.conf.json` has a strict CSP (no remote origins, no `unsafe-eval`; `wasm-unsafe-eval` and `blob:` workers are for pdf.js) and `withGlobalTauri: false`. PDFs are untrusted input; keep it that way.
- pdf.js worker, CMaps, standard fonts, wasm decoders and ICC profiles are served/copied from `node_modules/pdfjs-dist` under `/pdfjs/` by a small plugin in `vite.config.ts`.
- `vite.config.ts` pins port 1420 with `strictPort`, because Tauri's `devUrl` expects exactly that port. Vite also ignores `src-tauri/` so Rust rebuilds don't trigger HMR.
- `src-tauri/gen/schemas/` is generated by the Tauri build. Don't hand-edit it.
- The release profile in `Cargo.toml` uses LTO, `panic = "abort"`, and `strip`.
